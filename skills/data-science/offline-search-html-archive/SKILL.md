# Offline Full-Text Searchable HTML Archive (from JSON corpus)

## Trigger
Use when the user has a JSON corpus (legal sentencias, regulations, documents — e.g. TC/El Peruano cases) and wants:
- readable HTML per document, AND
- a full-text search page that works OFFLINE via double-click on `file://` (no server),
- and/or an improved static search UI (filters, snippet, dark mode, export).

Proven on: 8,794 TC sentencias (El Peruano 2016-2021) → `html_casos_v2/`, `html_casos_v3/` (v3 añade semántica por co-ocurrencia) y `html_casos_v4/` (v4 añade header/normas/resolutiva/vinculante + paginación, toggle gráfico, fuente A−/A+, badge fechas; v4.1 whitelist de distritos + reasignación del campo limpio al dict; v4.2 token-match en campos discretos distrito/ley/ds/art; v4.3 votos singulares, casos similares por coseno, top-10 leyes, histograma lag, typos Levenshtein, fallback OR). Detalle por versión: `references/co-ocurrencia-y-campos-faltantes.md` (v3), `references/campos-extra-y-ux-v4.md` (v4), `references/distritos-whitelist-y-match-token.md` (v4.1/v4.2) y `references/similares-typos-or-v4-3.md` (v4.3); corpus en `references/tc-elperuano-casos.md`.

## Architecture (why it works)
```
Python build script (one pass over JSON):
  → casos/<fecha>/NNN_Tipo_Expediente.html        (readable doc per case)
  → datos.js   = window.CASOS = [ [num,tipo,distrito,demandante,sentencia,fecha,edicion,stem,fallo,derechos,ponentes,citas,resumen], ... ]
  → indice.js  = window.INDICE = { termino: "<delta-encoded postings>" }
  → index.html = vanilla JS UI (search, filters, tabs, dark mode)
```
- **`<script src="datos.js">` works on file:// — `fetch()` does NOT** (CORS-blocked in Chrome). Always emit data as `window.X = ...` JS files.
- **Inverted index with delta-encoding**: postings lists are sorted ascending; encode as `chr(33 + delta-1)` per consecutive delta, `~<delta>~` for big gaps. Decode LAZILY per term in JS (Map cache) — never decode all 4M postings at load. Result: 25.7 MB → 15.3 MB raw, instant search after ~2-4 s load.
- **Token normalization must be IDENTICAL in Python (index build) and JS (query)**: lowercase + strip diacritics (NFD), tokens `[a-z0-9]{3,}`, same STOP set, same stemmer. Any drift = 0-result bugs (see Pitfalls).

## Build steps
1. Inventory corpus: count JSONs, total text MB, per-field population (empty/sucio fields).
2. Extraction per doc: numero, tipo, distrito, demandante, sentencia, fecha, edicion + semantic fields:
   - `fallo`: FUNDADA/INFUNDADA/IMPROCEDENTE (regex near "declar...")
   - `derechos`: keyword→category dictionary (pension, salud, debido proceso, ...)
   - `ponentes`: regex `PONENTE <NAME>` / `VOTO DE LOS MAGISTRADOS <NAMES>`
   - `citas`: regex `STC 00296-2007-PA/TC` / `Expediente NNNNN-YYYY-ZZ/TC`
   - `resumen`: first ~420 chars after "ASUNTO"
   - `demandante` completo: regex "interpuesto por don/doña X" — the JSON field is often truncated ("don Frank") while the full name lives in the text.
   - `header` (v4): DEMANDADO / MATERIA / JUEZ — regex `\bCLAVE\s*:?\s*([^\n|]{2,80})` on **texto[:500] ONLY** (see Pitfalls: body text pollutes the header).
   - `normas` (v4): `PAT_LEY = \b(?:LEY|L\.)\s*(?:N[°º]\s*)?(\d{3,5})` (N° optional — "Ley 26790" has no N°), `PAT_DS = \bD\.?S\.?\s*(?:N[°º]\s*)?(\d{2,3}-\d{2}-[A-Za-z]{1,4})` (keep trailing letters: "003-98-SA"), `PAT_ART = \bart[ií]culo\s+(\d{1,3}[a-z]?)`. Index with field prefixes: `ley:25212`, `ds:003-98-sa`, `art:56` → searchable as `ley:25212`.
   - `resolutiva` (v4): tramo `HA RESUELTO|RESUELVE` → hasta `Publ[ií]quese|SS\.|S\.\s` (re.S), cap ~800 chars → rendered as a highlighted box at the TOP of the case page ("Parte resolutiva").
   - `vinculante` (v4): bool regex `precedente vinculante|car[aá]cter vinculante` → badge ★ + field `vinculante:1`.
3. Index terms: metadatos x3 weight + texto (cap ~12K chars/caso) + prefijos `5:<first5>` + stems `s:<stem>` + citas. ~100K terms / ~8M postings for 8.8K docs.
4. Write HTML per case: barra (breadcrumb + tema + imprimir), cabecera con badges (fallo/ponente/citas), grid metas, TOC lateral from `<h3 class="seccion">`, fallos citados links `../index.html?q=<expediente>`, `?q=` highlight + scroll, selección→nota con localStorage, `@media print`.
5. UI index.html: search box + pills (tipo/año/fallo) + rango fechas + orden + tabs (nube/distritos/gráfico/favoritos) + export CSV/JSON + autocompletado (sugerencias desde Object.keys(INDICE), startsWith, con conteos).
6. **WSL/NTFS performance**: writing thousands of small files one-by-one to /mnt/d (drvfs) is ~17-64 files/s. ALWAYS write to /tmp (ext4, instant), then `cp -r /tmp/stage/ /mnt/d/...` (~8.8K files in 42 s). This is the difference between 5 min and 9 min.
7. Verify like a human in the browser: type real queries ("LIMA", "Vela Albornoz", `"abuso del derecho"`, `fallo:fundada derecho:pension`, `pension NOT onp`), click filters, tabs, open a case, check ?q= highlight, dark mode toggle, note save, export. Confirm counts and that links resolve to real files.

## Pitfalls (all hit and fixed in real sessions)
- **Stopword parity**: if Python filters "del" at index time but JS does not filter it at query time, `"abuso del derecho"` → AND with empty set → **0 results**. Same STOP list both sides; JS `.filter(t => !STOP.has(t))`.
- **Phrase `"..."` extraction**: removing the phrase from the query leaves 0 tokens for the AND. Fix: phrase TOKENS join the AND set; the exact-phrase match is a RANKING BOOST only (the stored snippet is short; the phrase may not appear in it even when the doc matches).
- **Synonyms must OR into the SAME term set**, never as extra AND sets: `pension NOT onp` broke because a "pension" synonym map included "onp", added as an extra AND conjunction → empty. Expand each term to `{term, 5:prefix, s:stem, sinonimos}` then union postings of all of them into ONE set.
- **Field parser greedy regex**: `(fallo|derecho|...):([a-z0-9\s\-\.]+)` swallows `fallo:fundada derecho:pension` whole into `fallo`. Fix: value = `[^\s:]+(?:\s+(?!\w+:)[...]+)*` — a field ends when another `palabra:` appears.
- **Enum fields (`fallo:`) need EXACT match, not `includes`**: `includes("fundada")` matches "INFUNDADA". Compare equality.
- **Autocomplete pill keys with spaces** need `CSS.escape()` when re-selecting via querySelector.
- **`?q=` from case pages**: links must be `../index.html?q=...` AND index.html must read `new URLSearchParams(location.search).get('q')` on init, or citation links do nothing.
- **Section detection in legal text**: keyword set + prefix match beats an all-uppercase heuristic — magistrates' names ("MIRANDA CANALES", "SS.") are uppercase too and create false headings.
- **Dirty source metadata**: scraped JSON often has garbage in fields (distrito="DEMANDANTE" for 1,359/8,794). Recover from text: `CORTE SUPERIOR DE JUSTICIA DE <X>`, fallback `<Ciudad>, <día> de <mes>` in the date line, `.upper()` for grouping. Report the dirty counts to the user — it's a data-quality finding, not a UI bug.
- **Distrito (and any enum field) needs a 3-layer clean, and the CLEANED value must be written back into the dict**: (1) blacklist of header labels (DEMANDANTE, DEMANDADO, JUEZ, ESPECIALISTA, BENEFICIARIO, SOLICITADO, SENTENCIA DE VISTA, PROCESO, DEMANDA, FAVORECIDO, APELANTE, JUEZA, REGIONAL, DEL...); (2) WHITELIST of real domain values (~60 Peruvian judicial districts) — a value is accepted ONLY if it's in the whitelist, otherwise recover from text; this is bulletproof against invented names ("MARÍA", "FELICITAS" never pass); (3) date-fallback regex must accept month with capital OR lowercase ("de Abril" and "de abril"). CRITICAL BUG HIT: the loop computed `dist = extraer_distrito(...)` for datos.js but never assigned `d['distrito'] = dist` before `generar_caso(d, ...)` → datos.js said AYACUCHO while the per-case HTML showed JUEZ (the raw field). After cleaning any field, ALWAYS write it back into the dict. This is only caught by a test that reads the GENERATED HTML on disk (assert the card value), not by unit-testing the extraction function alone. Result after fix: 252 distinct values → 42 (all real), 0 garbage.
- **Discrete/enum query fields need TOKEN-match, not substring**: `distrito:ica` matched HUANCAVELICA because `norm(val).includes('ica')`. For enumerated fields (distrito, ley, ds, art) match on full word tokens: split the query value on non-alphanumerics, normalize both sides, require every token to appear as a whole word (`' ' + norm(field).replace(/[^a-z0-9]+/g,' ') + ' '` contains `' tok '`). This keeps `distrito:lima` matching LIMA NORTE/SUR/ESTE (lima is a whole token there) while rejecting HUANCAVELICA for `ica`. Keep substring for identifier-ish fields where partial match is desirable (numero:01379 → "01379-2021-PA/TC", ponente:Miranda → MIRANDA CANALES). Testable in isolation with node on a pure `matchCampo` function.
- **Missing key field → recover from text, NEVER the filename stem**: when `numero` is None, `json_path.stem` as fallback leaks "039_Cumplimiento_s-n" into titles (936/8,794 cases). Write `extraer_numero(texto, campo)`: (1) honor a valid campo, (2) regex on the text AFTER normalizing line breaks (`re.sub(r'\s*/\s*\n\s*', '/', texto)` joins "EXP. N° 03718-2015-PC/\nTC"), (3) clean fallback "s/n". Validate the match looks like a number (`\d{4,5}-\d{4}`) before accepting.
- **Generator must be importable for tests**: wrap the main build loop in `if __name__ == "__main__":`. A top-level loop over 8.8K docs executes on `import` and hangs pytest. Without the guard, TDD on extraction functions is impossible.
- **rsync to destination WITHOUT `--delete`**: if you write to /tmp stage then `rsync -a --delete stage/ destino/`, it deletes everything not mirrored in stage — index.html, the generator itself, SPEC, tests (all lost in one run). Stage is not a mirror of the destination; use plain `rsync -a` or explicit `--exclude` for project files.
- **Header fields (DEMANDADO/MATERIA/JUEZ) MUST be extracted from `texto[:500]`, not the whole text**: the body of a fallo mentions "demandado" constantly ("INDEBIDAMENTE A LA ONP, SE DECLARE NULO..."), which pollutes the extracted value and the search chips. ~80% of real DEMANDADO headers live in the first 500 chars; the rest are body noise. Verified: 0 dirty headers after limiting to the cabecera slice.
- **Normas regex quirks**: "Ley 26790" often has NO "N°" (`N[°º]\s*` must be optional); "D.S. N° 003-98-SA" must keep trailing letters or you get "003-98-". Validate the extracted number looks like a norm before indexing.
- **datos.js grows fast with text-heavy fields**: adding resolutiva (long text) per case grew datos.js 5.3 → 10.0 MB. Acceptable for file:// (load ~2-4 s), but keep resumen capped (~420 chars) and resolutiva capped (~800 chars) or the JS payload balloons.
- **Graph "only shows 2016-2021" is often a DATA fact, not a bug**: if the corpus is publications from a newspaper archive, publication years are bounded by the corpus; RESOLUTION years may span wider (2000-2021 here, 42% coverage). Fix: toggle "Por publicación" | "Por resolución" using the second date field, with a coverage note.
- **UI controls that reorder/filter must call the COMPUTE function, not the RENDER function**: `#orden` listener called `pintarResultados()` but the sort lives inside `buscar()` → changing the select did nothing. Fix: `$('orden').addEventListener('change', () => { pagina = 0; buscar(); })`. Same class of bug for dates: `input type="date"` only fires 'change' when the picker closes — listen to 'input' AND 'change' with ~300 ms debounce so typing gives immediate feedback.
- **User-visible filter feedback**: even when a date filter works, users "don't notice changes" without visible feedback. Add a badge next to the inputs ("📅 2021-01-01 → hoy ✕" with click-to-clear) that appears the moment a filter is active.
- **Font-size controls (A−/A+)**: users on 4K/1366 screens want adjustable text. Two buttons adjusting `document.body.style.fontSize` (base 13 px, clamp 11-18 px), persisted to localStorage, applied on init. Cheap, high perceived value.
- **Numeric pagination**: "Mostrar más resultados" (incremental 50) is not enough once queries return 1,000+ results — users expect page numbers. Render `◀ 1 2 3 … N ▶` (window of ±2 around current, ellipsis for gaps), click → `pagina = p; pintarResultados(); scrollTo(top)`.
- **Semantic layer (offline co-occurrence, no embeddings)**: precompute `cooc.js` = `window.COOC = {term: [[rel, score], ...]}` from doc-term co-occurrence (frequency as the main signal, PMI as a log-adjustment: `score = co * (1 + max(0, log(N*co/(dfa*dfb))))`). Two passes: (1) global df, filter rare (df<~10) and ultra-common (>60% of docs) terms; (2) pairs only between eligible terms, capped at ~60 terms/doc for O(n²) sanity. Emit SYMMETRICALLY (both directions). **Filter boilerplate** (legal filler: fojas, recurso, demanda, agravio...) so "pension" relates to "onp"/"previsional"/"normalizacion", not to "fecha"/"fojas". UI: chips under the search box; click appends `OR <rel>` and re-runs search. ~0.5 MB / ~2K terms for 8.8K docs.
- **Build runs >60 s in foreground**: run the generator with `background=true, notify_on_complete=true`; `process wait` clamps at 60 s, just wait repeatedly.
- **Cosine similarity between docs: O(k²) explodes on frequent terms** (v4.3): pair loop over all docs sharing a term — a term present in 3,500 of 8,794 docs = ~6M pairs just for that term → 12+ min CPU at 90%. Fixes that made it ~30 s: (1) hard df cap `max_df = 300` (terms in >300 docs are too generic to discriminate anyway); (2) per-term, only the **top-20 docs by weight** (`docs_con_t.sort(key=-w)[:20]`) — discarded pairs are the lowest-contribution ones, quality barely moves. ALWAYS benchmark on 2,000 docs before the full run (2K docs ≈ 6 s → extrapolate).
- **Similarity/co-occurrence output must be SYMMETRIC**: emit both directions (out[a] AND out[b]) when writing pairs a-b; storing only a<b means a UI lookup from the other side returns nothing. (Same lesson as cooc, re-hit in similares.)
- **Post-loop computations (similares) need a second pass over the HTML**: similares can't be computed until ALL docs are processed. Keep texts in memory (`corpus_textos[doc_idx] = texto` in the first loop) — re-reading 8,794 JSONs in the second pass is pure waste. Re-generate only the case HTMLs that have similares, passing the block as an arg to `generar_caso(d, stem, similares=s_list)`.
- **Inter-case links inside per-case HTML need `../` prefix**: a case lives at `casos/FECHA/stem.html`; links to other cases must be `../FECHA/stem.html`, NOT `FECHA/stem.html`. Bug hit: similares block emitted `href="2016-08-04/139_....html"` → resolved to `casos/2016-08-01/2016-08-04/...` (broken). Fix pattern `href="../{fecha}/{stem}.html"`, then batch-fix existing files with `re.subn(r'href="(\d{4}-\d{2}-\d{2}/)', r'href="../\1', html)` across all case files.
- **Typo suggestion (Levenshtein ≤2) only fires when NO prefix-5 matches**: the `5:<first5>` postings give implicit typo tolerance — "jubilasiom" already matches via `5:jubil` so no suggestion shows (and search works). A real typo needs no shared 5-prefix: "penssion" → suggests "pension". Test with a term that has no 5:-prefix hit, and skip index keys containing `:` (internal prefixes) when scanning for the nearest key. Add a clickable "¿Quisiste decir: X?" button that sets the query and re-runs.
- **Fallback OR needs a real DOM node for its notice**: if AND returns 0 with ≥2 terms, retry with the UNION of per-term postings and show "⚠️ se muestran resultados con CUALQUIERA de ellos". Bug hit: wrote to `$('info')` but `.info` is generated INSIDE `#lista` — no element with id="info" exists → silent no-op. Add a dedicated `<div id="aviso-or">` before `#lista`, toggle display, and hide it on normal queries.
- **New boolean/enum fields must be wired in 4 places**: adding `voto:singular` required: (1) parseQuery campo list, (2) the field regex alternation, (3) idxCampo map, (4) a filter branch. Forgetting any one = field silently ignored. Same for `vinculante` (done in v4).
